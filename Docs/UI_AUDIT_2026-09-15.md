# Mythos Log — UI audit and design proposal

## Approved scope update

The subsequent user decision supersedes the dashboard and skill-detail proposals below: preserve dashboard skill tiles, artwork and charge; add optional dashboard-only and app-wide icons; simplify only header/tab chrome. On Skill Detail, remove the bottom Log Actions section and preserve the floating Log action. Review, Goals and History refinements are approved. Broader icon/button restyling remains a proposal.

## Recommendation

Keep the app’s warm, understated character. Use **More for hierarchy, Manage Skills for lists, Settings for forms, and the new widget for progress visuals**. Refine the Dashboard first, then Skill Detail, Review, History and Goals.

This is a **source-based audit of the current working tree**, including existing uncommitted work. Findings describe the implemented view hierarchy and styling, not screenshots of every rendered state. No production UI was changed for this audit. Layout, contrast, VoiceOver, keyboard and device behavior still need visual/device verification. No numerical usability scores are assigned.

## Proposed dashboard

- Keep the seven skills in the existing **2–3–2 portrait arrangement**. Use **4–3 on wider layouts**; do not compress four labelled items across a narrow phone just to copy the widget.
- Each item: **thin weekly ring → centered skill icon → skill name → weekly total with units**. All circles share a size and stroke weight.
- Keep actual totals visible even after a ring reaches 100%; put level, charge details and character art in Skill Detail and the existing This Week sheet.
- Use the user’s chosen skill order. Keep the small widget’s top-two behavior as a separate convention.
- Keep a quiet date/header, This Week and a secondary menu. Use a warm flat background and generous separation between rows.
- Tap a skill to open its detail, where Log stays visible. Keep long-press logging as an optional shortcut. Consider an explicit Log entry point in the header if direct dashboard logging is a priority; test discoverability before changing tap behavior.
- Show one small static exception badge per tile using an explicit priority: unresolved import, pending rank change, then ordinary attention. Keep all details reachable; never silently drop lower-priority states.
- At larger text sizes, allow a two-column or list presentation and vertical scrolling. Do not shrink names to preserve a fixed viewport.

This keeps the dashboard useful beyond the widget: the widget can be icon-only, but the app should retain names and totals. Preserve character artwork in the places where it has room and meaning.

## Findings and changes

### 01. Simplify each skill to one ring, one icon and two short labels

**First · Dashboard**

**Observed:** The default seven-skill view already uses a 2–3–2 arrangement and thin rings, but each tile also includes character art, a fraction, a level, a signed charge meter and optional badges.

**Suggestion:** Keep the 2–3–2 arrangement on portrait phones. Put the skill icon in the ring, the skill name underneath and a short weekly total below it. Move level and charge into the detail or existing This Week sheet. Keep character art in detail, roster and reveal screens. Use 4–3 only on wider layouts.

### 02. Flatten the command strip

**First · Dashboard**

**Observed:** The header combines a date kicker, This week chip, two menus, a gradient surface, gradient outline and tinted shadow. Its layout menu also contains Apple Health sync.

**Suggestion:** Use a simple date/header row, retain This week, and consolidate secondary actions into a neutral overflow menu. Keep layout, reorder and Health sync clearly named rather than nesting sync under layout. Maintain a consistent 16-point page margin.

[Source](/Users/joshgourgey/Coding/Mythos Log/MythosLog/Views/Dashboard/DashboardView.swift:300)

### 03. Fix the misleading Save for later action

**First · Logging**

**Observed:** Save for later calls dismiss() without persisting the working draft. The label implies a save that this path does not perform.

**Suggestion:** Replace it with Cancel or remove the duplicate dismissal action and retain a clearly labelled close control. Only use Save draft if draft persistence is implemented. Keep one primary Save Log / Complete Session action.

[Source](/Users/joshgourgey/Coding/Mythos Log/MythosLog/Views/Habits/HabitDetailView.swift:376)

### 04. Consolidate the surface treatments

**First · Shared styling**

**Observed:** V4Card has a hardcoded cream fill, two borders and a shadow. More destination cards use a simpler single border. Dashboard panels and tiles add their own white fills, gradients and borders.

**Suggestion:** Take More as the reference: one warm background, one subtle surface, one fine border where grouping needs it. Reserve material for the tab bar. Use open spacing for ordinary sections; avoid a card inside every card. Change the heavier screens first and keep Settings unchanged.

[Source](/Users/joshgourgey/Coding/Mythos Log/MythosLog/Views/Components/V4Style.swift:155)

### 05. Make attention cues still and readable

**First · Accessibility**

**Observed:** Dashboard rank indicators and unmatched-workout badges repeat their animations indefinitely without a Reduce Motion check. RankChangeRevealView already reads Reduce Motion. GameDashboardTile’s custom accessibility summary includes level and charge but omits the visible weekly fraction.

**Suggestion:** Use static badges by default, brief feedback after a user action, and the existing Reduce Motion pattern everywhere. Add actual/target plus units to the dashboard accessibility summary. Keep status symbols and words so color is never the only signal.

[Source](/Users/joshgourgey/Coding/Mythos Log/MythosLog/Views/Dashboard/DashboardView.swift:1584)

### 06. Bring everyday progress above configuration

**Next · Skill detail**

**Observed:** The screen gives the rank artwork a large hero, followed by week history, calibration, progression, goals and linked habits. This makes everyday logging share space with setup and game mechanics.

**Suggestion:** Lead with compact skill identity, weekly progress and the existing date-aware Log action. Keep the calendar and recent logs immediately accessible. Make rank artwork an expandable section or roster destination; group calibration and progression under secondary disclosures. Preserve the selected-date wording on Log.

### 07. Preserve the grouped rows; reduce extra framing

**Next · Review**

**Observed:** Review already groups skills by urgency, which is useful. It also has a diagnostic summary, hint, decorated container and 118 points of bottom padding; the root shell separately reserves tab-bar space.

**Suggestion:** Keep the urgency groups and direct Log actions. Use one concise summary, quieter section headers and More-style rows. Replace the fixed bottom allowance with the shared safe-area spacing after checking on device. Keep This Week and Last Week unmistakably separate.

### 08. Show an overview, then a selected skill

**Next · History**

**Observed:** The screen stacks the combined chart, a full effort ranking, overall summary, skill picker, another chart, skill summary and recent resolutions. This makes the reader traverse two levels of analysis in one long page.

**Suggestion:** Start with period controls and one chart. Offer Overview / Skill views or a compact skill selector. Put detailed resolutions behind a disclosure. Keep the existing selected-series emphasis and accessible chart descriptions; label baseline share clearly.

### 09. Reduce competing status and explanation text

**Next · Goals**

**Observed:** A goal card presents a status pill and can also add Needs attention or Attention viewed for this week. The empty state explains both goals and skill baselines in multiple paragraphs.

**Suggestion:** Keep title, progress, deadline and one status as the main card. Make acknowledgement a secondary action and avoid showing green success styling as if viewing attention resolved the underlying goal. Shorten the empty state to a sentence and create action; put the full explanation behind help.

### 10. Use a small, intentional set of styles

**Next · Typography and icons**

**Observed:** The code mixes serif titles, rounded black-weight headlines, heavy tracked uppercase kickers and several level-pill implementations. Skill icon containers vary from 30 to 48 points and use different fills, weights and corners.

**Suggestion:** Keep serif for rank titles and More’s editorial headings. Use system semibold for names, regular for supporting text and monospaced digits for totals. Reuse one icon component with ring, list and plain variants; a progress ring should only appear where it conveys progress.

### 11. Standardise the editing pattern

**Next · Forms and sheets**

**Observed:** Habit editor and managed skill settings use native forms, while logging uses a custom sheet with large header, repeated dividers, compact increment chips and a two-button footer. Habit editor calls the skill picker Stat domain.

**Suggestion:** Use Settings as the reference for configuration forms. Keep logging purpose-built but compact: skill/habit, amount, date, optional note and one save action. Standardise Cancel/Save placement, inset spacing and sheet detents. Rename Stat domain to Skill; use consistent Rank, Level, Baseline and Goal terminology.

[Source](/Users/joshgourgey/Coding/Mythos Log/MythosLog/Views/Habits/HabitEditorView.swift:23)

### 12. Check small controls and narrow layouts

**Next · Touch and text sizing**

**Observed:** The unmatched badge is explicitly 30×30, the log close icon 28×28, and several plain action chips have small padding. The dashboard name is fixed at 15 points with scaling down; tab labels are fixed at 11 points.

**Suggestion:** Keep small visuals but give interactive controls at least a 44×44 hit region without overlapping neighbors. Use scalable text styles, fewer columns or a row layout at accessibility sizes, and wrapping instead of shrinking critical labels. Confirm actual hit areas and truncation on device.

### 13. Protect the strongest reference screens

**Later · More and Manage Skills**

**Observed:** More has clear hierarchy and destination cards. Manage Skills uses a scannable native list with clear edit/reorder behavior. Settings is already a clean grouped list.

**Suggestion:** Keep these layouts. Only align shared icon weight, background tokens and terminology if needed. Consider reducing Manage Skills’ descriptor/calibration secondary text after the higher-priority work. Make no Settings redesign.

### 14. Carry the calmer language into first-use and exception screens

**Later · Onboarding and supporting flows**

**Observed:** Onboarding uses a large animated aura, uppercase step kickers and repeated cards. Roster, rank changes, review detail and workout attribution have their own combinations of cards, pills and action treatments.

**Suggestion:** Use a simple numeric step indicator and Manage Skills-style choice rows. Keep rank artwork and celebration in roster/reveal. Use one concise verdict plus expandable details for past reviews; use explicit primary and secondary actions for workout attribution. Apply the shared spacing and surface components throughout.

### 15. Keep navigation quieter than content

**Later · Navigation**

**Observed:** The custom tab bar uses material plus gradient stroke, an extra blurred outline, two outer shadows and another selected-item shadow.

**Suggestion:** Retain the four tabs and floating shape. Remove redundant decorative layers before considering any structural navigation change. Verify selected state, VoiceOver and large-text labels. The content rings should carry the visual emphasis.

### 16. Give the same ring the same meaning across app and widget

**Next · Progress meaning**

**Observed:** The widget ring is weekActual / baseline, while the app uses weeklyTargetProgress; More’s overall ring represents level / maximum level. The widget ranks skills by level, while the dashboard follows the user’s sort order.

**Suggestion:** Define the weekly skill ring as progress against the same agreed weekly baseline/target everywhere and share the calculation. Keep More’s rank ring visibly labelled as rank. Preserve user order on the full dashboard; treat the small widget’s top-two ranking as a deliberate exception. Verify over-target and zero-target cases.

## Screen coverage

- **Dashboard + all three layouts — Highest priority:** Simplify the default grid; align the optional card layouts with its typography and metrics.
- **More — Preserve:** Use its hierarchy and restrained destination cards as the reference.
- **Manage Skills + skill settings — Preserve / polish:** Keep native lists and forms; align identity and wording.
- **Settings — Preserve:** No redesign proposed.
- **Skill detail + calendar + history sheet — Refine:** Prioritise weekly progress, logging and recent entries; disclose setup detail.
- **Habit detail + editor + log sheet — Refine / fix:** Unify edit actions and fix Save for later wording.
- **Review + past reviews + explainer — Refine:** Preserve urgency grouping; reduce framing and redundant space.
- **Weekly review detail — Refine:** One verdict, compact recap, then expandable per-skill and import detail.
- **Goals + goal editor — Refine:** One clear status and action hierarchy; quieter supporting explanation.
- **History — Refine:** Separate overview and selected-skill analysis.
- **Roster + rank reveal + rank changes — Preserve / polish:** Keep character art and milestone moments; match shared controls.
- **Unmatched workouts — Refine:** Clear attribution action, secondary create action, quiet ignore action.
- **Onboarding — Refine later:** Simpler steps and choice rows; concise explanation of baseline and rank.
- **Tab bar + shared components — Refine:** Consolidate surfaces, typography, touch regions and motion behavior.
- **Summary widget + Quick Log widget — Reference / align later:** Keep summary widget; optionally bring Quick Log’s gradient panel into the same flat style.

## Proposed shared rules

- **Surfaces:** warm page background, subtle card fill, a single hairline border. Avoid tinted shadows and double outlines on ordinary content.
- **Spacing:** 16-point phone margins; 8/12 points within rows; 16/24 between groups. Let safe-area insets reserve room for navigation and sticky actions.
- **Type:** system semibold names; regular body and caption text; serif reserved for rank/editorial titles; one low-emphasis section-label style. Support Dynamic Type.
- **Icons:** skill color for identity; consistent medium-weight symbols. Ring containers for actual progress, simple tinted containers for navigation or lists.
- **Status:** neutral by default; warning/danger for exceptions; icon or text alongside color. One visible status per compact item with fuller detail available.
- **Actions:** one strong primary action per sheet or section. Use quiet text/outline controls for secondary actions and consistent Cancel/Save/Done wording.
- **Progress:** one agreed weekly ring calculation, a clear target label, and totals that remain meaningful above 100%. Do not visually conflate rank, weekly progress and charge.
- **Motion:** brief, purposeful feedback. Respect Reduce Motion; reserve celebration for milestones.

## Suggested implementation sequence

1. **Dashboard pilot:** implement the icon-ring tile and flat header, with representative empty, normal, complete, at-risk and import states. Fix misleading dismissal wording and motion behavior alongside this.
2. **Component consolidation:** settle surface, section header, skill identity, status and button variants based on the pilot. Keep Settings untouched and visually regression-check More/Manage Skills.
3. **Information hierarchy:** simplify Skill Detail, Review, History and Goals using those components. Preserve access to all existing actions and data.
4. **Supporting screens:** align sheets, onboarding, roster and workout attribution; polish navigation last.

## Verification before accepting implementation

Check a small and a large iPhone, iPad/wide view, default and accessibility text sizes, VoiceOver, Reduce Motion, light appearance (the app currently forces light mode), keyboard-open sheets, long skill/habit names, 0/1/2/7/more-than-7 active skills, zero/partial/complete/over-target progress, rank changes and unmatched imports. Validate primary and secondary button hit areas, contrast on actual composited backgrounds, scroll clearance and the selected date used for logging. The separate widget should also be checked in system light/dark/tinted appearances.

These are planned checks, not completed results. The proposal is ready for discussion; app changes are intentionally not part of this audit.
